# HTTP API

## Status and access

Milestone 3 implements local exercise catalogue and workout logging APIs. No authentication or per-user ownership exists yet; `custom` distinguishes custom exercises from built-in catalogue entries, not users. Keep loopback binding and do not publish these write operations before the deployment/authentication milestone.

OpenAPI JSON: `/v3/api-docs`. Swagger UI: `/swagger-ui/index.html`. Springdoc 3.1.1 is pinned for Spring Boot 4 compatibility; HTTP tests verify both endpoints. Generated documentation describes DTOs and validation; this document explains business rules and error cases.

## Exercise representation

```json
{
  "id": 1,
  "name": "Bench Press",
  "category": "Moninivelliike",
  "primaryMuscleGroup": "Rinta",
  "equipment": "Levytanko",
  "notes": null,
  "custom": false
}
```

IDs are opaque positive integers generated by PostgreSQL. `custom` is assigned by the server and cannot be changed through the request DTO. Built-in exercises are read-only. Responses are explicit records, never serialized JPA entities.

Write bodies contain `name` (required, maximum 100 characters), and optional `category`, `primaryMuscleGroup`, `equipment` (each maximum 50) and `notes` (maximum 2000). Surrounding Java whitespace is stripped; blank optional strings become null. Blank/missing names fail validation. Limits apply after normalization. Metadata is free text, allowing Finnish labels without fixing a taxonomy prematurely. Names must be unique case-insensitively across both built-in and custom exercises. This is not accent-insensitive or fuzzy matching.

## Browse and search

`GET /api/exercises?q=bench&page=0&size=20` returns HTTP 200:

```json
{
  "items": [],
  "page": 0,
  "size": 20,
  "totalElements": 0,
  "totalPages": 0
}
```

The body above illustrates an empty result; a matching query returns exercise objects in `items`. Defaults: empty `q`, page 0, size 20. Query maximum length is 100 before trimming; page is zero-based in 0–1,000,000 and size is 1–100. The page cap prevents ORM offset overflow at extreme inputs. Search matches a literal case-insensitive substring of the name. `%` and `_` are ordinary search text, not SQL wildcards. Empty/whitespace search browses all exercises. Results sort by database `lower(name)`, then ID; this is deterministic, not a promise of Finnish dictionary collation. Pages beyond the last return empty `items` with the actual total count.

`GET /api/exercises/{id}` returns one exercise (200), 404 for an unknown positive ID, or 400 for an invalid/nonpositive ID.

## Create and replace custom exercises

```sh
curl -i -X POST http://127.0.0.1:8080/api/exercises \
  -H 'Content-Type: application/json' \
  --data '{"name":"Oma soutu","equipment":"Käsipainot","notes":"Oma variaatio"}'
```

POST returns **201 Created**, the exercise JSON and a relative `Location: /api/exercises/{id}` header. All API-created exercises are custom.

`PUT /api/exercises/{id}` replaces the editable fields of a custom exercise, returning **200** and the updated object. Supply `name`; omitted optional fields are cleared to null. This is full replacement of editable fields, not PATCH. ID and origin stay unchanged. A built-in exercise returns 403; unknown ID returns 404. A name collision returns 409 and rolls back the update. Concurrent edits currently use last successful write behavior; optimistic versioning is not implemented.

There is no DELETE endpoint. It returns 405 for these paths. This refers to catalogue exercises, not logged workout entries. Database foreign keys now restrict deleting a referenced catalogue record. Workout-entry deletion behavior is defined below.

## Errors

Errors use `application/problem+json` and Spring `ProblemDetail` fields (`type`, `title`, `status`, `detail`, `instance`). Business errors and validation instructions use Finnish. Invalid body fields also include an `errors` array, for example:

```json
{
  "type": "about:blank",
  "title": "Virheellinen pyyntö",
  "status": 400,
  "detail": "Tarkista pyynnön kentät, tunniste ja sivutusparametrit.",
  "instance": "/api/exercises",
  "errors": [{"field":"name","message":"Nimi on pakollinen."}]
}
```

- 400: malformed/missing JSON, invalid field values, ID, pagination or search length.
- 403: attempted edit of a built-in exercise.
- 404: exercise does not exist.
- 409: database integrity conflict, including duplicate names. The database enforces uniqueness even for racing requests.
- 405/415: unsupported HTTP method/media type handled by the framework.
- 500: unexpected application failure; generic response and private server log.

Responses never include SQL, rejected field values, exception class names or stack traces. Do not publish private diagnostic logs. No database entity or internal Hibernate state appears in the success contract.

## Operational health

`GET /actuator/health` returns 200 `{"status":"UP"}` when healthy and 503 `{"status":"DOWN"}` after dependency failure. Internal components and probe groups remain hidden/disabled. Only health is exposed through Actuator, separately from Swagger.

Flyway requires a working database at startup. Initial connection/migration failure stops startup rather than creating a running endpoint returning 503. `/` remains 404; no frontend exists yet.


# Workout logging API (Milestone 3)

These endpoints remain local-only and unauthenticated. They record data; RIR/e1RM and progression calculations are not implemented. PUT replaces editable fields rather than patching individual fields.

## A first workout through Swagger

Use a normal browser; the VS Code in-app browser prevented Swagger request editing in Roope's testing. Expand the operation, click **Try it out**, edit the **request body**, then Execute. Response examples remain read-only.

1. `GET /api/exercises?q=bench` and copy the returned exercise ID. Do not assume catalogue IDs or use the workout ID in its place.
2. `POST /api/workouts` with `{"date":"2026-10-22","title":"Testiharjoitus"}`. Copy the returned workout ID.
3. `POST /api/workouts/{id}/exercises` with `{"exerciseId":1}` using the actual catalogue ID from step 1. Copy the returned **logged-exercise ID**, which differs from the catalogue ID.
4. `POST /api/workout-exercises/{id}/sets` using the logged-exercise ID and the example below.
5. `GET /api/workouts/{id}` to see ordered exercises and sets together.

Completed set example:

```json
{
  "weightKg": 60.25,
  "repetitions": 8,
  "rpe": 8.5,
  "setType": "WORKING",
  "completed": true
}
```

To prepare an unfinished set, POST `{}`: load/repetitions/RPE are null, set type is WORKING, completion is false and order appends. GET/PUT/DELETE the returned set using `/api/sets/{id}`. A zero load is valid, but a completed set needs a supplied load and at least one repetition.

## Workouts

- `GET /api/workouts?page=0&size=20`: summary envelope (`items`, `page`, `size`, `totalElements`, `totalPages`), newest `date` then ID first. Same page limits as exercises. Summaries omit nested exercises/sets.
- `POST /api/workouts`: 201 plus Location and a workout object with an empty exercise list.
- `GET /api/workouts/{id}`: 200, metadata plus `exercises`, each including its catalogue exercise and ordered `sets`.
- `PUT /api/workouts/{id}`: 200, replace metadata while preserving all logged exercises/sets.
- `DELETE /api/workouts/{id}`: 204, delete that workout and its child logged exercises/sets. Other workouts and all catalogue exercises remain.

Metadata body: required ISO `date` (`YYYY-MM-DD`); optional `title` (100), `notes` (2000), `startedAt` and `endedAt`. Blank title/notes normalize to null. Times are ISO instants with an explicit UTC offset (for example `2026-10-22T14:00:00Z`) and represent points in time. The training date is supplied independently; it is not silently derived from the server's timezone. End requires start and cannot precede it. Equal start/end is allowed. Future dates are not blocked. Omitted optional metadata is cleared on PUT.

## Logged exercises

- `POST /api/workouts/{id}/exercises`: body requires positive catalogue `exerciseId`, optional notes (2000). Returns 201 plus Location. Display order appends after the maximum order, starting at zero. An exercise can appear more than once in one workout.
- `GET /api/workout-exercises/{id}`: 200 with catalogue details and ordered sets.
- `PUT /api/workout-exercises/{id}`: replace `displayOrder` (required, 0–1,000,000) and optional notes. Catalogue and workout references stay fixed; remove and add an entry to change its catalogue reference.
- `DELETE /api/workout-exercises/{id}`: 204, remove this logged entry and its sets, preserving the parent workout, other entries and catalogue exercise.

Orders are unique within a parent. Gaps are valid and deletion does not renumber siblings. Moving onto an occupied position returns 409 and rolls back notes/order changes. Use an unused position for individual moves; an atomic reorder-all operation is not implemented. Concurrent appends may conflict on the same next position; a failed 409 can be retried after reloading.

## Sets

- `POST /api/workout-exercises/{id}/sets`: 201 plus Location, new set; omitted `setOrder` appends.
- `GET /api/sets/{id}`: 200, one set.
- `PUT /api/sets/{id}`: 200, replace performance/type/completion fields. Omitted `setOrder` preserves the existing position; omitted performance fields clear to null, type defaults to WORKING and completion defaults to false.
- `DELETE /api/sets/{id}`: 204, remove only this set. Missing resources return 404, including repeated deletes.

Fields: `setOrder` integer 0–1,000,000 (unique per logged exercise); `weightKg` exact decimal 0–9999.99 with at most two decimal places; `repetitions` integer 0–1000 for drafts, 1–1000 when completed; optional `rpe` 6–10 in 0.5 steps (at most one decimal); `setType` WARMUP or WORKING (default); `completed` defaults false if omitted or null. Drafts may omit weight/repetitions. Completed sets must supply both. Zero weight is allowed. Numeric strings are not part of the contract; use JSON numbers.

RPE is a subjective exertion entry, not measured performance. Weight is recorded exactly as entered in kg; there is no automatic per-hand multiplication for dumbbells. RIR and maximum/volume calculations are deferred to Milestone 4 and later metrics work. Changing a custom catalogue name changes the name shown for its references; no historical name snapshot is stored.

Validation violations, invalid timestamps/enum values and incomplete completed sets return 400. Missing workout/entry/set or catalogue IDs return 404. Duplicate sibling order or database integrity conflicts return 409 with no partial update. Delete endpoints are actual data deletion, with no undo/trash system; use disposable workouts for testing. Authentication/ownership checks remain required before exposing any of this beyond loopback.
